# Спринт модуля 2: план і рефлексія

## Мета спринту

Мінімальний робочий прототип: донор реєструється, заповнює профіль, бачить, коли йому можна здавати знову, знаходить найближчий центр і веде історію донацій. Людина, якій потрібна кров, створює запит, а сумісні донори поруч на нього відгукуються. Усе покрито тестами й API-документацією і розроблено через гілки, Pull Request і code review.

## Критерії готовності

- [ ] Демо: «зареєструвався → профіль → коли можна здавати → найближчий центр → запис в історію» працює.
- [ ] Демо: «створив запит на кров → сумісний донор відгукнувся → автор бачить донора й закриває запит» працює.
- [ ] UML-діаграми (use case, класів, послідовності) і схема БД — [uml.md](uml.md), [database.md](database.md).
- [ ] Обґрунтування архітектури та інструментів — [architecture.md](architecture.md).
- [ ] ≥ 20 модульних тестів і журнал результатів — [test-log.md](test-log.md).
- [ ] Інтеграційні тести API і їх результати — [test-log.md](test-log.md).
- [ ] API-документація у Swagger — [api.md](api.md).
- [ ] GitHub: окремі гілки, злиття в `main` тільки через PR, кожен PR схвалює (Approve) ревьюерка, не авторка.
- [ ] Підсумковий звіт і фінальна презентація з демо, планом і рефлексією спринту.

## Сценарій демо (≈ 7 хв)

1. Відкрити <http://localhost:5124>, зареєструватися.
2. Профіль: група A(II) Rh−, стать, дата народження, координати → «Можна здавати вже сьогодні».
3. «Центри»: список від найближчого з відстанню в км.
4. «Історія»: додати донацію сьогоднішньою датою в найближчому центрі.
5. Повернутися в «Профіль»: «Через 90 дн. — з …» (жінка, цільна кров).
6. «Запити» → «Створити запит»: A(II) Rh−, критично, центр «Поділ», телефон. Увійти як донор 0(I) Rh− → «Ваша група підходить» → «Я допоможу» → з'являється телефон. Повернутися до автора → видно донора → «Кров знайдено».
7. Показати Swagger (`/swagger`): Authorize → `GET /api/eligibility`.
8. Показати GitHub: список PR з рев'ю і зелений CI, журнал тестів.

## Рефлексія спринту

Ретроспективу провели всією командою після завершення спринту. Коротко: технічну частину модуля 2 виконали повністю й із запасом (14 задач, 60 модульних і 16 інтеграційних тестів), але командний процес відстав, історія комітів не показує реальний внесок кожної учасниці. Це головне, що виправляємо в наступному спринті.

### Що вдалося

- Закрили всі 14 запланованих задач модуля 2 (34 SP): реєстрація і вхід (JWT), профіль донора, калькулятор наступної здачі, список центрів за відстанню, історія донацій, вебклієнт.
- Тестів значно більше за мінімум: 60 модульних (при вимозі ≥ 20) та 16 інтеграційних, усі проходять.
- Уся інтеграція в `main` пройшла через 14 Pull Request, жодного прямого коміту в `main`, крім стартового.
- Підготували повну документацію: UML (6 діаграм), ER-схему БД, обґрунтування архітектури, API-документацію (Swagger / OpenAPI).
- Порядок робіт спрацював: каркас бекенду (B-02) і схема БД (B-01) були першими, тому решта задач будувалася на готовій основі.
- Налаштували CI на GitHub Actions: тести запускаються автоматично на кожен PR.

### Що не вдалося

- Не вели задачі як Issues на GitHub, тож прогрес по беклогу видно лише в документах, а не в репозиторії.
- Тести розподілені нерівно між учасницями: 27 / 12 / 12 / 9.

### Чому так сталося

- Спринт тривав лише тиждень, тож пріоритетом був робочий прототип і виконання формальних вимог, а не процес рев'ю.
- Гілки створювали ланцюжком (кожна від попередньої), бо задачі залежали одна від одної. Через це PR було зручно зливати разом у кінці, а не по одному.
- Посеред спринту додали задачу B-28 (запити на кров, 5 SP) — без неї демо не показувало головну ідею продукту. Це забрало час, і найбільше тестів довелося на ту, хто робила бекенд і B-28.

### Інші спостереження

- CI і журнал тестів, що генерується з `.trx`, заощадили час: результати тестів не треба було переписувати вручну.
- Swagger виявився зручним не лише для документації, а й для ручного тестування API під час розробки.
- Вебклієнт замість мобільного дав змогу показати наскрізний сценарій за тиждень, але це відхилення від дорожньої карти, яке треба пояснювати.
- Дизайн клієнта (темна тема, PR #12) робили без задачі в беклозі — дрібні задачі теж варто вносити в план.

### Що змінюємо в наступному спринті

- Кожна учасниця комітить і відкриває PR зі свого акаунта GitHub.
- Рев'ю обов'язково з коментарями: мінімум один змістовний коментар від ревьюерки та відповідь авторки до злиття.
- Зливаємо PR по ходу спринту, щойно задача готова, а не все в останній день.
- Ведемо задачі як Issues на GitHub і прив'язуємо до них PR (`Closes #N`).
- Нові задачі посеред спринту додаємо лише замість інших, щоб не перевантажувати план.
- Розподіляємо тести рівномірніше: кожна пише тести до свого коду.
